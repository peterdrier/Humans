**PR A of three.** Renames the SystemSettings section to **Settings**, gives it a typed table for the app-wide event values, and ships the operator screen that copies the existing values into it. **Nothing reads the new table.** Deploying this changes nothing a user can see.

The original single PR created the table *and* repointed ~20 sections at it in one shot, which cut every reader over to an empty table and left the site waiting on a human. That is the wrong order. This is the first of the three steps:

| **B** | Point the readers at the Settings contract, once the values are across. | later |
| **C** | Drop the duplicated columns from `event_settings`. | later |

## The migration

**One migration, `20260821131645_AddSettingsEvent`, CLI-generated against `SettingsDbContext`.** `Up()` is one `CreateTable("settings_event")` and one `CreateIndex` on `Status`. `Down()` drops `settings_event`, the table that same migration creates.

No `INSERT`, no `UPDATE`, no `Sql()`. **No `Drop*` or `Rename*` of any kind against an object that already exists** — not `system_settings`, not `event_settings`, not any index, key or constraint on either. `dotnet ef migrations has-pending-model-changes` is clean for `SettingsDbContext` and `ShiftsDbContext`.

`Section.cs` keeps `sentinelTable: "system_settings"`. Renaming the context renamed its history table (`__EFMigrationsHistory_SystemSettings` → `__EFMigrationsHistory_Settings`), so on an existing database the section reads an empty history; the sentinel is what tells `SectionMigrationRunner` the tables are already there, so it must name a table that exists *before* the pending migrations run.

### How the migration was regenerated

The branch previously carried `AddAppEventSettings`. `dotnet ef migrations remove` could not run — it connects to check applied migrations and there is no Postgres on this machine — so the repo's `/ef-regen` procedure was used instead, with one deliberate deviation.

ef-regen restores the snapshot from `origin/main`. Here that would have been actively harmful: `origin/main`'s snapshot names the entity `Humans.Domain.Entities.SystemSetting`, the branch renamed it to `Humans.Settings.Domain.Setting`, and diffing the live model against that snapshot invites EF to emit a drop/recreate of `system_settings`. The snapshot was restored from `d9ac3974f^` instead — the branch's own commit immediately before the migration was added, which already has the renamed namespaces and does not yet know about the event table. Same "as if this migration never happened" baseline, sourced from the branch rather than main. The generated `Up()` above is the proof it worked.

## Carrying the values across — operator screen, not a migration

`settings_event` ships empty. An operator fills it from **`/Settings/Admin/Carry`** ("Carry event settings", under Settings in the admin sidebar).

- Three counts — Shifts event rows, already carried, remaining — plus a per-row table naming each event, its year, whether it is the active cycle, and whether it is here yet.
- **Done is `Remaining: 0`.** At zero the button disappears.
- Writes only rows the table does not already have, keeping each row's `Id` so `Rota.EventSettingsId` and `EventGuideSettings.EventSettingsId` still resolve. Idempotent and safe to re-run.
- **No deadline.** Nothing reads `settings_event`, so there is no window and no outage. Run it whenever; step B is what makes it matter.

It lives in **Settings**, not Shifts: the write belongs to the section that owns the table. It reads the source rows through `IBurnSettingsService` in `Humans.Shifts.Contracts` like any other cross-section read, so no `[CrossSectionWrite]` is involved. Not a cycle — `Humans.Shifts` does not reference `Humans.Settings.Contracts`.

## The contract

`ISettingsServiceRead` is gone; there is one interface and it has no `Read` suffix.

```
ISettingsService : IApplicationService
    GetValueAsync / SetValueAsync                 — the key/value store
    GetActiveEventSettingsAsync
    GetEventSettingsByIdAsync
```

`SaveEventSettingsAsync` is deliberately **not** on it. Nothing outside Settings writes the event values, so the write sits on the internal `Service` class, reachable only by the section's own two screens. The key/value `SetValueAsync` does stay on the interface — Email's send-pause flag and Monitor's last-run stamp have been written from outside since long before this issue, and `ISystemSettingsService` always carried both. Moving those two keys into their own sections is separate work.

`EventSettingsStatus { Active, Inactive, Deleted }` replaces the old `IsActive` bool, stored as a string column. Deleting a cycle is a status change, never a row removal — other sections store the row's `Id`. Keeping a bool *and* an enum would have given the same fact two homes.

## New cross-section surface

- **`IBurnSettingsService.GetAllAsync(CancellationToken)`** in `Humans.Shifts.Contracts`, returning `IReadOnlyList<BurnSettingsInfo>`. The carry screen has to enumerate every cycle and only `GetActiveAsync`/`GetByIdAsync` existed. Retires with the carry screen. Flagging it because new public surface is normally Peter's call.

`BurnSettingsInfo` exposes no active flag, so the carry cannot tell from the list which cycle is live. It calls `GetActiveAsync()` once and marks that id `Active`, everything else `Inactive` — copying them all as `Active` would break the at-most-one-active invariant on the new table. The alternative, widening `BurnSettingsInfo`, is more public surface for no gain.

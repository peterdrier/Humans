Renames the SystemSettings section to **Settings**, gives it a typed app-wide event settings table, and moves every cross-section read of the event calendar off Shifts and onto the Settings contract. Three of the eight acceptance criteria are deliberately partial — see the AC table below; the rest of #1104 is the retirement step.

## Which context owns which table

| Table | Context | Notes |
|---|---|---|
| `system_settings` | `SettingsDbContext` | the cross-cutting key/value store, unchanged |
| `app_event_settings` | `SettingsDbContext` | **new.** Public year, event name, timezone, gate-opening date, the build calendar and its four sub-period offsets, early-entry capacity/allocation/close, active flag |

## The migration

**One migration, `20260821105115_AddAppEventSettings`, CLI-generated against `SettingsDbContext` only. It creates `app_event_settings` and nothing else: no `INSERT`, no `UPDATE`, no `Sql()`, no `DropTable`, no `DropColumn`. It moves no data and does nothing destructive.** `dotnet ef migrations has-pending-model-changes` is clean for both `SettingsDbContext` and `ShiftsDbContext`.

`Section.cs` keeps `sentinelTable: "system_settings"`. Renaming the context renamed its history table (`__EFMigrationsHistory_SystemSettings` → `__EFMigrationsHistory_Settings`), so on an existing database the section reads an empty history; the sentinel is what tells `SectionMigrationRunner` the tables are already there, so it must name a table that exists *before* the pending migrations run.

## Carrying the values across — operator screen, not a migration

`app_event_settings` ships **empty**. An operator fills it from **`/Shifts/Admin/EventSettingsCarry`** ("Carry event settings", under Shifts → Temp in the admin sidebar).

- The page shows three counts: Shifts event rows, already in Settings, remaining — plus a per-row table naming each event, its year, whether it is active, and whether Settings holds it.
- **Done is `Remaining: 0`.** At zero the button disappears and the page says so.
- It writes only rows Settings does not already have, keeping each row's `Id` so `Rota.EventSettingsId` and `EventGuideSettings.EventSettingsId` still resolve. Idempotent and safe to re-run.
- It lives in Shifts because Shifts owns the source rows; Settings must not read them. `AppEventSettingsMoveService` is an orchestrator over `IShiftManagementService` and `ISettingsService`, marked `[CrossSectionWrite]`, and it touches no repository.

## 🛑 READ THIS BEFORE MERGING — deploying this causes a site-wide outage until an operator runs the carry screen

**`app_event_settings` ships empty. From the moment this deploys until an operator opens `/Shifts/Admin/EventSettingsCarry` and clicks the button, the site has no active event.**

`ISettingsServiceRead.GetActiveEventSettingsAsync` returns `null` for that entire window. This PR repointed roughly twenty sections at that call, so they all read "there is no active event" simultaneously:

- **Shifts** — `/Shifts` renders the no-active-event page. No volunteer can browse or sign up for a shift.
- **Gate** — no active event means no event timezone and no event year: the gate terminal cannot resolve "today", pre-fill the gate-crew roster, or write Attended participation.
- **Store** — `/Store` and `/Store/Admin/Catalog` resolve no active catalog year; new team orders have no year and the `OrderableUntil` deadline gate has no "today" to compare against.
- **Tickets** — `EventParticipation` derivation and `Participation/Backfill` have no year to scope to.
- **Cantina** — no gate-opening/strike-end range, so the roster is empty.
- **Event Guide, Early Entry, Camps, Scanner, Agent, the member dashboard** — same, each in its own way.

**Duration is entirely operator-controlled: it lasts exactly as long as it takes someone to log in as Admin and click one button.** Minutes if it is planned, indefinitely if nobody is told. Whoever merges this needs an admin available at deploy time.

The carry screen is idempotent, so it can be run the instant the deploy is live, and re-run safely if anything fails partway.

**No fallback was added, deliberately.** A Settings→Shifts read fallback would close the window completely, and it is a reasonable thing to want — but it is Peter's call, not something to decide inside this PR. Flagging the consequence rather than pre-empting the decision.

## Assessment summary

Issues is a small, coherent section (score 260 → 258, loc 2482 → 2466,
cogP95 10, cogMax 21) that answers **six question-shapes** with one service,
one repository, one controller and one page. It was in better structural shape
than its score suggests: no caching decorator to go stale, no parallel event
table, no cross-domain navs, and the one genuine oddity — `Section` being a
free string rather than an enum — is load-bearing and documented.

The value was not in structure. It was in **three user-visible defects and a
localization path that was wired up and then ignored**, all of which survived
because nothing read the section end to end:

- Search was case-sensitive, so "ticket" missed every issue titled "Ticket".
- Nine `Issue_*` toast keys were translated into five languages and referenced
  by nothing — the controller hardcoded English at fourteen call sites.
- The attachment hint told users "PNG or JPEG, max 5 MB" while the service has
  accepted WebP up to 10 MB.

And a second cluster in the docs: `authorization.md` documented a controller
and an auth filter that **do not exist**, `Issues.md` attributed a dependency
to a section that does not exist, named the wrong notification interface, and
described three architecture-test assertions that the test does not make.

The tests thread found the sharpest gap: the visibility predicate — the rule
that decides who can see whose issues — was exercised only through a
substitute repository returning `[]`, so flipping its `OR` to an `AND` passed
every test in the suite.

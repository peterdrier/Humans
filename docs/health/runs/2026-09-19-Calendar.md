## Retro

The best thing the target shape bought was finding 17. No tool reported it and no thread looked for
it; it exists only because 3c wrote down "order once — nothing downstream re-derives it to fix it"
before anything was scanned, and the scan then found the sorts. It also cost the least: writing
the target took minutes and it was the only lens that caught a whole-section shape claim.

The threads disagreed once, and the majority was right. Freshness reported both `debt.yml` rows
still live; Inbox, Tests and History each reported them resolved with proof, and main re-grepped the
branch before deleting them. A thread's absence verdict is a hypothesis
(`memory/process/review-finding-triage.md`), including when it is the thread whose whole job is
freshness.

The same rule caught a thread in the other direction. Prose named four unused `@using` lines; two of
them were load-bearing, because its grep looked for `Namespace.` and views name those types
unqualified. The build found it in one pass. A grep that proves an absence has to match every shape
the thing can take, and for a C# using that means unqualified type names, not just qualified ones.

A comment this run wrote to make a comment true was itself untrue, and Codex caught it in review
(`#discussion_r4051925191`). `ICalendarRepository.UpsertExceptionAsync` was documented as taking
exactly one occupied identity argument and never matching stale storage; the legacy all-day
migration path passes both and matches precisely on the stale instant. The corrected comment came
from reading the callers and the repository body; the wrong one came from reading the signature,
the unique indexes and the happy path, which agreed with each other. When a comment claims an
argument combination never occurs, the only proof is every call site, and the strike that rewrites
a comment deserves the same verification budget as one that deletes code.

The run's own mistake was `dotnet clean`. A cold `dotnet build` of `Humans.Base` fails in this
container — `@addTagHelper` directives stop resolving, so `<partial>` and every `asp-*` attribute
parse as raw markup and `_Table.cshtml` and `_Pager.cshtml` produce 18 errors. It reproduces in a
pristine worktree at the same commit, after an explicit restore, non-incremental, and under a UTF-8
locale; CI builds the same tree and runs its tests, so it is the container and not the repo. What
made the earlier builds work was the pre-built `obj/`/`bin/` the container shipped with, and
`dotnet clean` removed it while I was chasing an unrelated error. Nothing about a diagnosis was
worth destroying the only build state in the container; the diagnosis could have run in a throwaway
worktree from the start, which is where it ended up anyway. There is no new `memory/` atom here —
the rule that covers it, `memory/process/section-doctor-no-sdk.md`, already exists and is what the
run followed once the compiler was gone.

## Needs Peter

1. **`CancelOccurrence` answers a forged POST with a 500.** `CalendarController`'s cancel path
   throws where the override path re-renders the form, so a POST naming a non-recurring event
   returns 500 rather than a 400 or a re-render. Both are hand-crafted-request paths, no UI reaches
   them. Should they match, and on which behaviour?
   **Answered 2026-09-20 — 400.** The cancel path returns `BadRequest` for an event that is not
   recurring. Not applied here: this PR promises no behaviour change, so the fix carries its own
   PR and tests. Tracked as nobodies-collective/Humans#1198.
2. **`CreatedByUserId` has no GDPR path.** Calendar persists the creating user's id on every event
   and contributes nothing to export or deletion. Every other section's personal data does. Is this
   an omission to fix, or is a creator id deliberately out of scope as authorship rather than
   personal data?
   **Answered 2026-09-20 — an omission, on the export side only.** Calendar contributes
   `CreatedByUserId` to the GDPR export. It contributes no deletion path: a calendar event is not
   personal data, so the event stays when its creator is deleted and the creator then renders as a
   deleted user, which is the accepted outcome. Not applied here, same reason as item 1. Tracked as
   nobodies-collective/Humans#1199.
3. **nobodies-collective/Humans#592 needs an edit.** Its design predates the
   `ICalendarFeedContributor` fan-out and proposes merging external occurrences inside
   `CalendarService` instead; every path in its Key files block names the pre-split layout. A run
   may not touch an issue. Reword it, or close it in favour of a contributor-shaped one?
   **Answered 2026-09-20 — close it.** Closed as not planned, with a comment naming the fan-out
   that superseded its design. Done.
4. **This container cannot build.** See Retro. Worth a look at what the Claude Code environment
   prebuilds, because a cloud run that loses `obj/` silently becomes docs-only.
   **Answered 2026-09-20 — investigated; does not reproduce, and the evidence is gone.** The
   container that failed was reclaimed overnight; the one that ran this investigation booted fresh
   and re-cloned the repo. On it, `dotnet clean Humans.slnx` followed by `dotnet build
   src/Humans.Base` succeeds with no errors, in the main checkout and in a pristine worktree alike,
   so a clean does recover on a healthy container. The environment is sound: the ASP.NET Core
   targeting pack is installed, `api.nuget.org` answers, the package cache is populated and the disk
   allowance is nowhere near spent. That leaves the original symptom — `@addTagHelper` not
   resolving, so `asp-*` and `<partial>` parse as literal markup — as a Razor build running without
   its resolved references, i.e. a half-written `obj/`. What cannot be settled after the fact is
   why: the leading candidate is the per-session disk allowance running out mid-run, where deletes
   keep succeeding while writes fail, which matches a `clean` that worked and a rebuild that never
   recovered. A run that hits this again cannot tell the two apart from the compiler output alone,
   so the diagnostic gap is tracked as peterdrier/Humans#1754.

**What the assessment missed that striking revealed.** The comment-volume finding. Five lanes'
worth of criteria and none of them asks "is the rationale in the right place" — I only saw it
from reading `Service.cs` end to end for the doc rewrite, and it is arguably the section's
largest single deviation from a standing project rule.

**Second-half retro.** The run broke a HARD RULE it had never read. `no-derived-aggregates-in-docs`
is in `memory/INDEX.md`, and I wrote counts into five files without checking whether a rule covered
them — the scorecard format itself invites it ("Tests | 57 in ..."), which is worth fixing in the
skill rather than in me. And the count that mattered was also *wrong*, which is the rule's own
argument: a hand-typed derived number drifts silently, and this one would have sent the queued
refactor at a method that has an external caller.

Two process notes. The destructive-ops baseline has a seeder, and running it clobbers unrelated
baselines' hand-written explanatory comments and reorders their entries — append by hand instead.
And `dotnet format whitespace` is a CI gate that a local `dotnet build` will not catch; it belongs
in the per-commit loop, not just before the PR.

## Sweep queue

- lesson: run `dotnet format whitespace --verify-no-changes` before every commit, not just before the PR — it is a CI gate a green `dotnet build` says nothing about, and this run shipped a red build over an object initializer in a test helper. Run the formatter rather than guessing at its rule.
- lesson: no counts in the scorecard or the run file. `no-derived-aggregates-in-docs` is a HARD RULE and the scorecard format invites breaking it ("Tests | 57 in ..."). Write the qualitative state — "every write path covered", "over the largeClass threshold" — never a method total, test count, route count or section rank. The dated reforge score in the history table stays: it is a measurement with a generator, not a hand-copied aggregate.
- lesson: never run the ratchet baseline seeder (`HUMANS_SEED_RATCHET_BASELINES=1`) to add one entry — it rewrites every baseline, dropping other people's hand-written explanatory comments and reordering unrelated entries. Append the single line by hand, keeping the file's newline style.
- lesson: when Peter answers the Needs-Peter queue in-session, keep working rather than deferring to a follow-up run. This run's queue came back the same day and all five approved items landed in the same PR, which is what moved the score at all. The queue is a checkpoint, not an exit.
- lesson: `cd` inside a backgrounded Bash call does not move the session; `cd` in a foreground call does. Run `pwd` once before the first write of a run and take the answer.
- lesson: do not conclude anything about a view from a grep. A backlink grep keyed on `asp-controller` said `CreditorStatement.cshtml` was a nav dead end; the file uses `asp-action`. Open the four or five views a section has.
- lesson: a duplicated table in a doc is a drift generator — replace it with a pointer, not a corrected copy. `Finance.md` restated Budget's route table and it was that copy, not the original in `Budget.md`, that went stale.
- lesson: when a section doc contradicts itself, believe the specific half. `Finance.md`'s summary and its Architecture section disagreed about which controller serves `/Finance`; the detailed lower section was right and the summary a reader hits first was wrong.
- lesson: a doc that names another section's surface in order to say what is *not* this section's must carry that section's file in its `freshness:triggers`, or the claim goes stale invisibly.
- lesson: dispatching lanes is not free. This run dispatched none — InspectCode ran as one background command and everything else was main-thread reading — and the assessment did not suffer. Reserve lanes for sections too big to read end to end, and prefer a background *command* over a subagent when the work is a tool invocation rather than judgment.

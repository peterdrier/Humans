## Assessment summary

First doctor pass over Stripe, the payments connector (reforge 65 @ 0.29.0, loc=753,
cogP95=11, cogMax=20): one interface, one implementation, two boot jobs, no tables, no
`DbContext`, no controller, no view, no resx, no route. The target shape
([`health.md`](../../../src/Sections/Humans.Stripe/Docs/health.md), written this run before
any scan) found the structure right as built and named two things it should not have: a
behavioural rule the code broke in one place, and one duplicated listing.

The rule is the section's whole contract — **a read returns `null` for the configuration
cases it checks; it does not turn a failure into a value.** Finding 1 is the one method that
broke it: with `STRIPE_TICKETS_KEY` unset, `GetPaymentDetailsAsync` threw out of Stripe.NET's
`StripeClient` constructor where its three siblings log and return `null`. Reproduced by
execution before being fixed. It is unreachable in production — the single caller gates on
`IsConfigured` and catches around the call — so no reached path changed behaviour; what
changed is that the configuration cases are now handled uniformly and pinned. The first
version of this run stated that rule far too broadly, and Codex caught it: finding 33.

Everything else was prose and coverage. The section carried a TODO for work that shipped
(finding 7), a DI extension type that exists nowhere in the tree (finding 11), a class doc
counting two tests where one exists (finding 3), and a layer of G5-migration provenance —
lane numbers, design-session dates, other sections' names as precedent (finding 10). The
test gaps (findings 15–18, 20, 21) sat over the checkout write guards, the signature
boundary, the event switch and both boot jobs' non-blocking contract;
`tests/Humans.Stripe.Tests` went from 21 to 37 tests.

sections by reforge score; 13 of 43 were blocked by open doctor PRs, which is the highest
blocked count any run has faced and worth watching — the never-doctored tier is down to

History thread reported `docs/sections/G5-SECTION-TEMPLATE.md` absent (it is present) and the
`2026-06-04` reconciliation-design pointer unresolvable (it resolves). Both were "this
reference is stale" claims about files outside the section, which is exactly where a
section-scoped grep returns a false negative. Neither produced an edit; each cost a check.

**What the assessment missed that striking revealed:** the guard for finding 1 is not what
the assessment said it was. The ranked entry read "restores the documented `null`" — but the
pre-change doc-comment promised `null` only for a missing *scope*, never for an unset key.
The reviewer caught it; the commit message and `Stripe.md` say the accurate thing (the guard
makes the four methods' contract uniform, and the doc-comment now covers the case it never
did). Second: the boot-job tests written alongside finding 2 do not cover finding 2. Every
path they exercise returns before the first network call, and `WebhookEndpointService` is
constructed inline from a `StripeClient`, so the deletion pass is unreachable from a test as
written. The reviewer refused to credit it, correctly; the collapse ships behind a reviewer
gate and a reasoned equivalence argument, not behind tests. That is worth naming plainly:
this section's two boot jobs are untestable past their configuration gates without a seam
none of them has, which is finding 30 below.

**The target over-claimed twice, and neither catch was mine.** Finding 19 (the round-trip
claim, true outbound only) and finding 33 (the "never throws" contract) are the same mistake:
writing the target shape's *aspiration* in the present tense, as though the code already held
it, and then propagating it into the section's invariant doc and the interface's doc-comment
where it becomes a promise callers can rely on. A target shape is allowed to describe what the
section should be — that is its whole job — but §4 is labelled **Invariants**, and an invariant
is a claim about what IS. The two must not be written in the same voice. Finding 19 was caught
by this run; finding 33 was caught by Codex, after the run had already shipped the claim into
three files and called the independence check a pass.

**Target diff:** none possible — first doctor pass, `health.md` written this run. One
correction landed on the target itself mid-run (finding 19: the round-trip claim was true
outbound only), and one section of it moved from "should change" to "reached this shape"
when finding 2 shipped. Next run gets the first real diff.

One auto-compaction occurred mid-Phase 4, between the reviewer gate on finding 2 being
dispatched and its verdict arriving. Phase 5's mandatory re-read of Phases 5–7 is what

is what both of this run's gates returned. Proposed edit to **Phase 4**: an APPROVE with a
correction is applied to the finding's description and the commit message before committing,
and the correction is named in the run file's retro — it is not a silent approval.

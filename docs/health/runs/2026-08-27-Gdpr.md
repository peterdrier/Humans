## Assessment summary

Structurally the section is already at its target: the contracts leaf, one internal
orchestrator, one internal controller, one `Section.cs`, and nothing else — the shape §2's
six question-shapes imply. Nothing was collapsed or rearchitected, and nothing needed to be.

What is off-target is its prose, and by a consistent amount: the section's comments and
docs describe the codebase as it stood two structural moves ago. A deleted project
(`Humans.Application`), a deleted `DbContext` (`HumansDbContext`), a deleted method
(`ProfileService.ExportDataAsync`), a controller the section has but three files deny it
has, two `design-rules.md` anchors that point at unrelated or nonexistent rules, and five
counts of lists the code owns.

One of those is not cosmetic (finding 1). Three separate documents justify the sequential
fan-out as a **thread-safety requirement**, resting on a shared `HumansDbContext` deleted
at nobodies-collective/Humans#858. `design-rules.md` §8a — the regulations — already
records that reason as obsolete and says why. So the section's own spec was telling a
reader that parallelising the loop would corrupt state, while the regulations said it
merely wouldn't help; and `gdpr-export.md` went further, naming as a *future* precondition
("if a future refactor gives each contributor its own context via `IDbContextFactory`") a
refactor that has already happened. Sequential stays — for the reason the code actually
has now.

Finding 2 is the run's one shape mismatch and is not struck: the JSON serialization of the
export document exists twice, byte-identically, in two sections.

Three lenses came back clean and that is worth stating: conformance (no rule keyed to
Gdpr; the general ones pass or are N/A), navigation and localization (both routes
discoverable and exited, the Guest dashboard card's two keys present in all six cultures),
and the inbox (no open issue on `peterdrier/Humans` touches Gdpr, no debt-ledger item is
Gdpr-owned).

## Retro

**What the selector got wrong.** Nothing in its ranking — Gdpr at the median was a good
pick, and a small section made full coverage genuinely full rather than aspirational. But
the blocked-set case-sensitivity defect bit for the second consecutive run and had to be
worked around by hand again. It is already queued as finding 15 on PR #1538 and is not
re-asked here.

**A low score is not health, and a *small* section is not health either.** Gdpr is 342
lines and scored 186, almost all of which is the fan-out seam counted once per registering
section — not surface to burn down. A run could have read that as "little here to find"
and it would have been wrong: the section carried a spec telling readers that
parallelising its loop would corrupt state, when the regulations had already ruled
otherwise.

**Wasted motion.** Two background test runs were launched and immediately stopped on a
mistaken belief that a backgrounded Bash call starts at the session root rather than
inheriting the working directory. It inherits it; the first launch was already correct.
Cost was two stops and a restart, and the mistake was mine rather than anything the skill
should change.

**What the assessment missed that striking revealed.** The Freshness lens reported
`docs/features/global/gdpr-export.md` clean, and that file carried the run's headline
false claim — in prose, in a section heading's body, with no dead symbol to resolve. The
lens checks that the names a doc uses resolve; this claim used only live names to say
something untrue. What caught it was Phase 4's own rule: once finding 1 was struck in
`Gdpr.md`, grepping the repo for the literal string `HumansDbContext` found it.

**And that sweep is where the run's own worst miss came from — it grepped a name, not the
claim.** Every copy of the false rationale that phrases it as "scoped section DbContexts"
rather than naming `HumansDbContext` survived the sweep untouched, including
`GdprExportService.cs:10` — the orchestrator's own class comment, which is the copy the
three documents finding 1 corrected had copied *from*. The review bot found it on the
first round (finding 22), along with a second statement in `gdpr-export.md` and a leftover
in the run's own new test. `grep -i "not thread-safe"` finds all seven sites in one pass;
`grep HumansDbContext` finds two. **A claim sweep is only a net if it greps the claim.**
Name the symbol *and* the sentence — a stale rationale outlives the type it was about,
which is the whole reason it is stale.

**The run wrote the defect it was striking.** Finding 13 cut counts of lists the code owns
out of `Gdpr.md`; §2 and §3 of the `health.md` written in the same commit then introduced
three fresh ones. Striking a class in the section's prose does not inoculate the prose the
run itself authors — and 3c's target doc is the most likely place to slip, because it is
written fast, from scratch, while attention is on getting the *shape* right rather than on
how the shape is phrased. **The prose a run writes goes through the same rules as the prose
it deletes.** No skill amendment: the skill already says so in as many words.

**Three rounds, one class, and the third is the interesting one.** The derived-count rule
was struck *out* of this section (finding 13), then broken by the target doc the same commit
wrote (23), then broken again by the sweep transcribing other runs' counts into living
ledgers (24). The first two are carelessness. The third is a rule the run did not have: **a
sweep is not a copy — the run file it reads is dated and its counts expire with it, while the
ledger it writes is read as current.** Anything a sweep carries becomes the sweeping run's
prose and takes its rules. That is the transferable one, and it is the sweep's rule rather
than the author's, so it is asked in `## Needs Peter` rather than only recorded here.

**What the target diff says.** First run on this section, so there is no previous target
to diff — but the target changed *within* the run, which is the same signal a run early.
§4's sequential invariant was drafted in 3c carrying the very reason finding 1 then
demolished, because 3c derives the target from the section's own docs and those docs were
wrong. Corrected in the same commit that fixed them, and `health.md`'s load-bearing
weirdness list now warns the next run that a doc calling this a thread-safety requirement
is drift, not a rule. A target derived from prose inherits the prose's errors; the
independence check does not catch that, because the error came from the section, not from
a scan.

## Retro

**What the selector got wrong: nothing, and that is worth saying.** Settings came up on
age-plus-churn with the largest churn figure in the pool, and the churn was real — the section had
been rebuilt twice over since its last run. A section that was just rewritten is exactly where
stale comments concentrate, because the rewrite moves code and leaves prose. The priority formula
found that without knowing it.

**Wasted motion: the threads over-claimed twice, and both times in the same direction.** The
Comments thread reported that `FinishingWeekend < 0` is enforced nowhere, having read `Validate()`
and not the attributes above it; the Prose thread attributed a reforge signal to a health.md
bullet that says something else. Both were readable as findings and both would have produced a
wrong change. The cost was re-reading the source myself, which is the cost the thread was supposed
to save. A reading thread that cites one enforcement site should be asked whether it looked for a
second — the attribute-plus-`IValidatableObject` split is a standing trap in this codebase, not a
one-off. Second-order: on a run whose whole subject is "these names are gone", `doctor.py trace`
reports every such name as MISS, which is correct and also exactly backwards from what the run is
claiming. Nothing here met the bar for filing against the skill, and no open issue named the
scripts or rules involved.

**What striking revealed that the assessment missed:** that finding 22 was the interesting one and
the assessment had it ranked twenty-second. The Comments thread's over-claim, once corrected,
stopped being a comment defect and became a test-coverage hole — the `[Range]`s really did run in
no test, so the "< 0" half of the section's headline invariant was unpinned. The assessment saw a
wrong comment; the strike found the reason the comment could stay wrong. Ranking by what the
finding *is* rather than by what it would cost to fix would have moved it up.

**The same defect twice, one round apart.** Findings 24 and 25 both ended in a per-section
absence test, and withdrawing the first did not make me re-read the second — it was sitting in
the same file, four lines below, asserting that `SettingsController`'s `[Authorize]` carries no
policy and no roles. What let it survive round one was the word "authorization": the atom carves
out authorization negatives, and I read a reflection assertion about an attribute as one. It is
not — the carve-out is for a request that exercises the route. The generalisable part is the
withdrawal itself: when a run drops one test under a rule, the rest of that run's tests are the
first place to look for the next instance, because they came from the same reading of the same
docs an hour apart. Both corrections are now in the atom.

**A fix that tripped the next rule along.** Cutting the stale reader enumerations meant writing a
sentence explaining why the list is gone, and the honest explanation was "each rebuild left a
shorter one behind" — which is PR archaeology in a current-state doc, caught on round three under
`current-state-docs-no-history`. The reason a thing was removed belongs in the run file and the
commit; the doc gets the standing instruction and nothing else. Both `health.md` and the invariant
doc carried it, and a third instance of the same class was sitting in the seams section.

**What the target diff says:** the target barely moved, and that is the finding. Two passes now
agree on the same shape, and the second pass's corrections were to the target's own claims — nine
`ISectionSettings` contributors, not one; Shifts and Camps reading the cycle directly — not to its
structure. A section whose target stops moving while its comments keep drifting is telling you the
code is settled and the prose around it is not, which is the opposite of the usual reading. No
new durable project rule came out of this run — the one `memory/` change is the sharpened
carve-out on an atom that already existed.

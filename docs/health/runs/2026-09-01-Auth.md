## Assessment summary

Auth is a horizontal owning `role_assignments`, and its jobs have nothing to do with each other:
temporal role assignment, and magic-link sign-in. reforge scored it 605 over 1,753 loc — the median of the
never-doctored tier — with cognitive complexity flat (p95 3, max 8 in
`RoleAssignmentRepository.ReassignToUserAsync`). The score is not complexity; ten of its points are
`missingReadSurface`, which is F31, a Peter-sized change.

What the section actually had wrong was *description*, not logic. Two repository methods existed for
callers that did not exist (F1, F2), and both doc comments named a real caller that calls something
else — the kind of comment that is worse than none, because it survives a grep. The caching
decorator's own test substituted a collaborator the decorator cannot have (F3), which is what let
one of those dead methods look alive for as long as it did. Further claims across the section's
five docs contradicted the code (F4, F5, F7–F13, F23–F26), including a paragraph asserting the
section has no caching decorator while `Section.cs` registers one five ways. Eight documented
invariants — cache invalidation, audit, the Board team sync, the `RoleNotActive` guard, the
best-effort notification, the two magic-link failure paths, and the bulk-revoke path's deliberate
silence — had no test at all (F21).

Behaviour was read by hand across both sign-in paths and the three write paths. No defect was found.
Two behaviour-shaped findings turned out to be naming, not bugs (F28) or a scan's mistake (F34).

## Retro

**What the selector/rubric got wrong.** Nothing in the ranking — Auth at the median of the
never-doctored tier was the right pick, and the tier split behaved. What it could not do was run:
`select-section.py` shells out to `gh`, which this container does not have, so the blocked set had to
be hand-built from the GitHub MCP tools into a `prs.json` the script could read (F35). The same gap
bit Phase 7. Neither is a judgment problem; both are the skill assuming a local machine.

**Wasted motion.** The Prose & surface thread (haiku) reported six dead resource keys and one
non-existent route. Five of the six keys were live and the route exists — `DebugController` has
`[HttpGet("CacheStats")]`. Verifying those seven claims cost more than the one real finding
(`Login_Hello`) was worth. On this run the cheap thread's yield was one finding against seven claims.
Whether that holds across runs is answerable from the other run files plus their cost comments, and
is worth answering once rather than per run — recorded as a Needs-Peter question rather than a rule,
because the fix is a dispatch policy, not a project rule.

**What the assessment missed that striking revealed.** That F2 and F3 are one finding, not two. The
assessment ranked "dead method" and "test substitutes the wrong collaborator" separately; striking
showed the second is *why* nobody noticed the first — the substitute was a data bag in the fixture's
own closure, so the dead method had one caller and it was the test that existed to test something
else. A ranked list that scores findings independently will keep splitting pairs like that; the
independence check catches the reverse case (findings that are all one scan) but not this one.

**The assessment's real failure: reading docs as evidence instead of as claims.** F41 and F43 were
both readable during Phase 3 and both were missed, and the reason is the same in each case. The
assessment treated a doc sentence as a fact about the code whenever the sentence was specific and
confident. `magic-link-auth.md` said signup replay is blocked because the account now exists; that
was a *proposal* in a design doc, never implemented, and it went into the target shape as shipped
behaviour. `data-access.md` said `IAdminAuthorizationService` answers board/coordinator/admin
questions; it answers exactly one, hardcoded to `Admin`. Neither needed new information to catch —
`VerifySignupToken` and `AdminAuthorizationService` are both a few lines long and were both in the
inventory.

The failure compounded: in review round 1 the false single-use claim was put to this run directly,
and it was defended by citing `Auth.md` as the doc that had it right. Three rounds later `Auth.md`
turned out to carry the same falsehood. A wrong belief sourced from docs got re-confirmed from docs.

The generalisable rule for the next run, which is why this is in the retro and not just the findings
table: **a doc claim about behaviour is a hypothesis to test against code, exactly like a scan
finding — including when the run is currently rewriting that doc, and especially when the claim is a
guarantee.** Phase 3's doc-truth pass verified each claim it *chose to rewrite*; it did not verify
the claims it left standing, and every one of F41, F41b and F43 was a claim left standing. Where the
claim asserts a security property, the corresponding user-facing copy is part of the surface too:
F41's promise was in the shipped email in all six cultures, and nothing in the run looked there until
a reviewer pointed at it.

**What the target diff says.** No diff to read — `Docs/health.md` is new this run, so 3c wrote the
first target rather than regenerating one. The next Auth run gets the first real comparison. Two
things in it were load-bearing immediately: §3's "the warm path should ask for rows and nothing else"
produced F2, and §4's "exactly one definition" of active-at-now produced F29. Neither came from a
scan. That is the target earning its cost on the run that wrote it, which is not the run it was
supposed to pay off on.

**Compaction.** The session auto-compacted once, during Phase 4 between strikes 2 and 3. Phase 5's
re-read rule did its job — the bookkeeping mechanics were re-read from the skill before any of this
file was written, and the phase-log format (`<iso-ts> <phase-id> <label>`) had in fact been lost:
one line was written malformed and was corrected from the commit timestamps.

## Assessment summary

First doctor pass over Calendar: the community calendar —
one-off and recurring team events with per-occurrence overrides — plus the personal iCal
feed orchestrator that shares the section but not its data path. The target shape
([`health.md`](../../../src/Sections/Humans.Calendar/Docs/health.md), written this run before
any scan) found the architecture right as built: one repository owning both tables, a §15
keyed-inner/Singleton-decorator pair, one silhouette per mutation, and a
table-free feed orchestrator.

What it found instead was **real user-visible defects and a documentation layer that had
drifted away from the code in a specific, checkable way.**

The headline defect: `Views/Calendar/List.cshtml` grouped occurrences by start date only
and always rendered a clock time. An all-day event displayed `00:00`; a three-day event
appeared on day one and vanished for days two and three. `Index`, `Agenda` and `Team` all
route through the section's `StartLocalDate`/`EndLocalDate`/`ShouldHideTimeLabel` helpers —
`List` was the only one that never did, since these views were first written.

The doc drift has one root cause worth recording: **`GenerateDocumentationFile` is set
nowhere in this repo, so CS1574 never fires and a green build says nothing about whether a
`<see cref>` resolves.** Calendar alone was carrying a crop of them, and a doctoring run is
currently the only thing that catches them. Alongside them, comments across the repository,
the service and the controller all asserted an `OwningTeam` navigation property that does
not exist on `CalendarEvent`, and `Docs/Calendar.md` named an architecture test
(`CalendarService_ConstructorTakesNoEfType`) that has never existed while attributing
further assertions to a test class that makes none of them.

And a run of documented invariants had no test behind them: deleting the code that
implements each left the whole suite green.

**The verification found a defect the whole assessment missed (finding 33).** The first
create POST answered **500**, and isolating it to a single changed field showed the cause:
`RecurrenceTimezone` posted empty. Model binding turns an empty posted string into null, and
`DateTimeZoneProviders.Tzdb.GetZoneOrNull(null)` throws `ArgumentNullException` instead of
returning null — so the guard that exists to reject an unknown zone never runs. The box is a
free-text `<input>` in `_CalendarEventFormFields.cshtml`, shared by Create and Edit, so

mutation-verified.

`CalendarService.ValidateTimezone` could not be reused: it treats blank as *valid*, because a
non-recurring event legitimately stores no timezone. The controller needs a zone object out of
the same field to convert the posted local times, so blank is unusable there — the form's
"recurrence timezone" doubling as the event's entry timezone is the underlying smell, and is
left alone.

Worth stating plainly: this is the same defect class as finding 3 (`ParseOriginal` throwing on

reading missed it. Reading found the throw that was reachable from a *route*; only exercising
the form found the one reachable from a *field*. A run that never renders the section is
blind to that half.

An all-day event is stored as `[local midnight, next local midnight)`, which is 24h on an ordinary Madrid day and 23h across the spring transition, so after it `start + 24h` lands at 01:00 the next local day, `EndLocalDate` advances, and the day-per-row views add a "continues" row that should not exist.

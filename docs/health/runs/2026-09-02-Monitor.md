## Assessment summary

First doctor pass over Monitor, the section carved out of AuditLog to own one job: read
Google's Drive Activity feed for the managed Drive folders and write an audit row for every
permission change the service account did not make. reforge scored it 95 at the anchor
commit (loc=613, cogP95=28, cogMax=28), the whole of which sat in one method.

The target shape ([`health.md`](../../../src/Sections/Humans.Monitor/Docs/health.md),
written this run before any scan) says the structure is right as built: one service, one
job, one controller with two read-only pages, no tables, no seams. Nothing about the
section's layout is wrong.

Two things were. First, the prose: the section's docs, csproj comments, `<remarks>` blocks
and test doc comments still describe the world before the carve-out — a service living in
`Humans.GoogleIntegration.Services`, an `ISystemSettingsService` that has since been
renamed, a job under `Contracts/`, an inbound Shell reference the section does not have,
five `design §N` citations that point at the wrong sections or at nothing, and two named
tests that do not exist (findings 2, 3, 8–19, 22, 23). One invariant was stated backwards:
`Monitor.md` said the scan "never throws to its caller", and the scan throws when every
resource fails.

Second, one concept spread across five fields and three methods.
`CheckForAnomalousActivityAsync` was 169 LOC at cognitive 28 because resolving a Google
`people/{id}` to a human name was interleaved with the scan loop rather than owned by
anything (finding 7). It is now a nested `PersonNameResolver` and the scan is 96 LOC at
cognitive 13.

No behavior bugs. Three invariants that only ever held by luck are now pinned (findings 4,
5, 6): the total-outage throw, the job's success/failure metric, and marker-before-audit
ordering.

The section's authorization and routing invariants are all pinned in
`tests/Humans.Integration.Tests`, which `build.yml` filters out of every CI run. That is
deliberate and permanent, so those assertions are local-only; the docs now say so rather
than citing them as enforcement (finding 13). One consequence has no CI-visible home at all
and is finding 26, below.

## Retro

**What the selector got wrong: nothing, but it nearly picked a section it should not have.**
The rubric's median-by-score rule landed on a 613-LOC section whose entire score was one
method, which made for a clean run. The rule has no way to know that; a section whose score is
one method and a section whose score is spread over forty are the same number to it.

**Wasted motion: the two combined-lens threads.** Combining Conformance with Prose & surface
saved one dispatch and returned nothing. Combining History with Comments returned 51 entries
with heavy overlap between the two lenses — the same comment reported once as history
narration and once as a prose defect — which cost more to deduplicate than a second dispatch
would have cost to run.

**What striking revealed that the assessment missed: the resource loop's failure semantics.**
The assessment saw finding 7 as a length problem. The first extraction plan had
`ScanResourceAsync` return a list, which would have discarded every anomaly found before a
mid-enumeration throw — a real behavior change, invisible in the diff, and not covered by any
existing test. The second-opinion gate is what caught it. A collapse whose safety depends on
where a `yield`-driven exception lands is not a mechanical strike, and the run nearly treated
it as one.

**The target diff:** none — this is Monitor's first run, so `health.md` was written from
scratch with nothing to diff against. Writing it before the scan did its job: findings 1, 3
and 7 all came from the gap between the shape the target derived and what the code does.

**One compaction, at bookkeeping** (peak main-thread context 288,927 tokens; the cost comment
on the PR reports both). It landed exactly where Phase 5's re-read rule expects it, and the
re-read is what put the sweep back on the rails: the compaction summary carried "apply the
queued items" and had dropped the routing table and the idempotence rule that say where and
whether.

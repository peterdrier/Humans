## Assessment summary

Cantina is a read-only aggregator with no tables, no `DbContext`, no repository and no EF
reference. It answers two questions — "how many are here each day this week" and "who exactly
is here on this day, and what do they eat" — plus a CSV of each, behind an Admin/CantinaAdmin
policy, and it never touches medical data. That part is in good shape and well pinned.

What it does **not** do is describe itself accurately. The section's prose describes a
different product from the one that ships, and the code carries two behavioural gaps that no
test doubts.

The target is now written at `src/Sections/Humans.Cantina/Docs/health.md`; this is the
section's first doctor pass, so there is no previous target to diff against.

### Findings, ranked

1. **[bug — queued] A human whose stored `DietaryPreference` is not one of the four canonical
   values disappears from the dietary breakdown.** `BuildDietaryBreakdown` increments
   `answered` for any non-empty preference but only buckets values it recognises, and
   `Unanswered` is then computed as `total − answered`. So an unknown value lands in no
   bucket at all and the breakdown no longer sums to the head count. The comment immediately
   above the branch states the intended rule — "Treat them as Unanswered for display purposes"
   — which is exactly what the code does not do. Both the weekly and the daily path. The write
   path filters against the canonical list, so the exposure is legacy or hand-edited rows;
   the code deliberately guards for that case and implements the guard wrongly.
2. **[bug — queued] Profile-less on-site humans render as "(unknown)" instead of their name.**
   `BuildProfileMap` keeps only users whose `UserInfo.Profile` is non-null and
   `ResolveBurnerName` reads `ProfileInfo.BurnerName`, so `UserInfo.BurnerName` — the field
   that carries the Users-side legacy fallback — is never consulted. `Cantina.md` documents
   the opposite ("Burner-name stitching reads `UserInfo.BurnerName`… falling through to
   `(unknown)` when absent"), and two DTOs promised a `DisplayName` fallback that no code
   performs. A coordinator's roster shows "(unknown)" where a name exists.
3. **[freshness — struck] The feature spec specified the inverse of the shipped UI**, on two
   points at once: it required a per-person table on the weekly page (removed when detail moved
   to the drill-down) and listed the per-day drill-down under "Out of scope (v1) … rejected as
   low-value" while its own Routes table shipped that page and its CSV. The drill-down had no
   user story at all.
4. **[delete — struck] 72 dead resx entries** — the 12 per-person-table column labels, orphaned
   in all six locale files when that table was removed. Referenced nowhere in the repository.
5. **[history — struck] The dated arrival/FODMAP design doc** (171 lines) narrated a merged
   branch through paths that have all moved (`src/Humans.Domain/`, `src/Humans.Application/`,
   `SharedResource.resx`, six line-number citations) and described a first-shift scan the code
   no longer performs. Its four live decisions moved into `health.md`.
6. **[freshness — struck] Names that no longer resolve**, across nine files: the service
   interface credited `IShiftManagementRepository`, `IProfileService` and `IUserService`;
   six DTO blocks sourced dietary from `VolunteerEventProfile`; the controller promised HTTP
   403 where the app redirects; `Humans.Domain`, `Humans.UI` and `Humans.Infrastructure`
   survived in four files after G5 deleted all three.
7. **[freshness — struck] The feature doc's freshness triggers watched the wrong section.**
   They pointed at the Shifts `VolunteerEventProfile` files — whose dietary columns are marked
   "RETAINED for prod-soak drop" — and not at `Humans.Users/Domain/Profile.cs` or
   `UserInfo.cs`, where the data the doc asserts about actually lives.
8. **[shape — queued] Four service methods over two questions.**
   `GetCurrentWeekStartOffsetForActiveEvent` / `GetCurrentDayOffsetForActiveEvent` exist only
   so the controller can resolve a default it immediately hands back to the service. Making the
   offset parameters nullable on the two async methods deletes 2 interface methods, 2 controller
   dependencies (`IBurnSettingsService`, `IClock`) and 2 private controller helpers.
9. **[efficiency — queued] The weekly path queries the same seven days twice.**
   `LoadWeeklyOnSiteUsersAsync` fetches the visible week, then
   `BuildFirstConfirmedOffsetByUserAsync` re-fetches every day from build start through the
   window's end, which includes all seven. The two scans are deliberately separate (see the
   load-bearing weirdness list) but the overlap is not deliberate.
10. **[tests — queued] Both defects sit in the two holes in the invariant matrix.** Every other
    invariant, negative access rule and trigger in the target has a pinning test; nothing pins
    unknown-value dietary bucketing or the burner-name fallback.

11. **[bug — queued, off-section] Account deletion leaves dietary and medical answers on the
    profile.** Surfaced by a review-bot finding on this PR's own GDPR wording, then verified:
    `UserRepository.AnonymizeProfileInternalAsync` clears seventeen profile fields and deletes
    the contact-field and volunteer-history rows, but never touches `DietaryPreference`,
    `Allergies`, `AllergyOtherText`, `Intolerances`, `IntoleranceOtherText` — or
    `MedicalConditions`, which is Art. 9 data. A deleted account keeps its dietary and medical
    answers attached to an anonymized profile. Users' code, not Cantina's, so queued rather
    than struck; the feature doc no longer claims the erasure guarantee it was inheriting.
    Possibly already in scope for the open right-to-erasure PR #1446.

## Needs Peter

1. **Unknown dietary value — bucket as Unanswered, or count it separately?** The comment says
   Unanswered; the code counts it as neither. One line either way, but it changes a displayed
   number. (Finding 1.)
2. **Burner name — is the `UserInfo.BurnerName` fallback meant to apply here?** `Cantina.md`
   says yes, the code says no, and profile-less humans currently show "(unknown)". Fix the code
   to match the doc, or the doc to match the code? (Finding 2.)
3. **Collapse the roster service from 4 methods to 2** by making the offsets nullable and moving
   default-resolution into the service? Removes 2 interface methods and 2 controller
   dependencies. Interface *reduction*, not addition. (Finding 8.)
4. **De-duplicate the weekly day scan?** The visible week is fetched twice per render. The two
   scans must stay logically separate; only the overlap would go. (Finding 9.)
5. **Two pinning tests** for the invariants behind findings 1 and 2, once you have ruled on them.
6. **Was the LOC-for-reforge-score substitution the right fallback** for selection when the
   score cannot be computed, or should a run with no compiler refuse to select at all?
7. **Environment — the blocker is narrower than this run first reported.** Investigated after
   the run, at Peter's prompt:

   - **The SDK does install from Ubuntu.** `apt-get install -y dotnet-sdk-10.0` gives 10.0.111
     from `archive.ubuntu.com`, which satisfies `global.json` (10.0.100 + `rollForward:
     latestFeature`). `dotnet tool restore` (Stryker 4.16.0) and `dotnet tool update --global
     Reforge` (0.29.0) then both succeed. The blocked host is not needed for any of that.
   - **It still cannot build this repo.** Every project fails `CS9057`:
     `src/Humans.Analyzers` is built against `Microsoft.CodeAnalysis.CSharp` **5.3.0**
     (`Directory.Packages.props`), and Ubuntu's 10.0.1xx band ships Roslyn **5.0.0.0**.
     `-p:RunAnalyzers=false` does not bypass it — the analyzer assembly is still loaded and
     version-checked before it is asked to run.
   - **There is no second source for the newer band.** `packages.microsoft.com` is reachable
     (200) but carries no .NET 10 SDK for noble — Microsoft defers to Canonical on 24.04 — and
     `apt-cache madison` shows 10.0.111 as the only version in any Ubuntu pocket. The band that
     carries Roslyn 5.3 comes from `builds.dotnet.microsoft.com`, which is 403.

   **So the fix is one of:** allow `builds.dotnet.microsoft.com` for this environment; bake a
   10.0.3xx/4xx SDK into the image; or pin `Microsoft.CodeAnalysis.CSharp` down to the band
   Ubuntu ships. The first is the smallest change and also restores `dotnet-install.sh`.

   **Either way the daily routine's setup block is now wrong** — it opens with `dotnet tool
   restore` on a container where `dotnet` does not exist. I could not edit the routine myself
   (`section-doctor-daily`, `trig_01DaFsf6UCrv7NiCAFxgExFr`, created via the HTTP API, so agents
   cannot update it). Replacement text is in the PR body under this item; it installs the SDK
   first, names the denied host so no future run burns time rediscovering it, and tells the run
   to degrade to docs-only rather than editing C# it cannot compile.

8. **Should account deletion clear the dietary and medical profile fields?** (Finding 11.)
   `AnonymizeProfileInternalAsync` clears seventeen fields and leaves these six, including
   `MedicalConditions`. Either the anonymization list is missing them, or the retention is
   deliberate and should be written down. Users' code, so it needs your call rather than a
   Cantina run's — and #1446 may already cover it.

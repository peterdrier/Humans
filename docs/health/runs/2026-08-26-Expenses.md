## Assessment summary

Expenses is a well-built section with a specific, repeated failure: **it documents and registers
gates that nothing asks for.** Several mechanisms, found independently, turned out to be one
shape. An authorization operation with no call site. A second one granted by the handler while the
controller hand-rolls the same check beside it. A whole resource-based handler wired into DI and
reachable only from its own tests. A service method the invariant doc names as the endorsement gate,
with zero production callers. And a cap field that the decision paths set and no path clears.

That last one is the finding worth Peter's morning. `MaxAmount` is the figure finance types on their
own decision form to pay less than the receipts total, and `Payable = min(Total, MaxAmount)` is the
only number the section allows payment math to use. `ExpenseRepository.FinanceRejectAsync` clears
the endorsement fields on the way back to Draft and does not clear the cap; `CoordinatorRejectAsync`
clears nothing. So a report rejected at €40 and refiled shows a payable of €40 against a €120 total
until somebody approves or endorses it again. No wrong money moves — both write paths overwrite the
cap before the Holded push — but the member and the review queue read a number nobody authorized for
that round. It is a two-line fix in one file and it is money-shaped, so it is Peter's, not this
run's (finding 1).

What the section gets right is worth saying, because several threads came back with nothing. The
resx set is clean: every key live, every culture at parity, every key prefixed. Nav is whole in both
directions. Every rule in `section-conformance.yml` passes. The layering is exactly what the
architecture asks for — one repository, one service, one handler, DTOs across every boundary — and
the full-service cross-section dependencies reforge flags (`IUserService`,
`IHoldedFinanceService`) are both there because Expenses genuinely writes through them.

The struck work is the doc half. `Expenses.md` claimed a `Profiles` dependency the section does not
have and stated the GDPR export does not read audit back, in a file that lists an `ExpenseAuditLog`
export slice eleven lines above. `data-access.md` named `ITeamService` where the code injects
`ITeamServiceRead`, and described `PerDiemKind` as a persisted column when it is a service argument.
The dated design docs described a SEPA payout pipeline and a personal IOU card that both left the
section, with no banner saying so. And a cluster of comments explained the section by reference to a
migration that finished — "moved into `Contracts/` at G5 lane 5b-5", pointing at a path that has not
existed since.

## Retro

**What the selector got wrong:** nothing, and the miss is informative. Expenses scored 287 on
public surface and complexity, and the run's headline finding is a field the decision
paths write and no path clears — invisible to every rule reforge scores. As on Store, the median pick found a
real defect by a measure blind to it. Worth noting the scores barely moved: 287 → 285, `loc`
4094 → 4071, `cogP95` and `cogMax` unchanged at 9 and 20. A run whose value is in findings and
corrected doc claims should not be expected to move a surface score, and the history table
should be read as a trend line, not a scoreboard.

**Wasted motion:** the section-scoped reforge ran *before* §3 of the target was written. The skill
puts the target ahead of every scan precisely so the shape is not read off the tooling, and the
target here was in fact derived from reading `Expenses.md` and the controller, not from the score —
but the ordering makes that unprovable from the transcript, which is the point of the rule. One
process slip, no rework.

**What the assessment missed that striking revealed:** the doc strike on `Expenses.md` surfaced
that the file contradicts itself within twelve lines (finding 6: an `ExpenseAuditLog` export slice
documented, then "the GDPR export does not re-read audit here"). Nothing in Phase 3 reads a doc
against itself — every thread reads docs against *code*. A section doc long enough to have sections
can disagree with itself, and that disagreement is free to find and needs no code read at all.

**What the target diff says:** there is no previous target — Expenses' first run, so `health.md` is
new. §3's "one authorization handler that owns the actor × operation × status matrix, and one
operation per thing a person can do. Nothing hand-rolls an ownership check beside it" is what turned
the separately-discovered artifacts of findings 2–5 into a class. §4's "only a decider sets
`MaxAmount`, on their own decision form" is what made the uncleared cap a violation rather than an
oddity; without that sentence written down first, a field that the decision paths set and none clears
reads as ordinary.

**What the review round cost, and what it was right about.** Two Codex findings, both verified
against the code and both real. The `no-derived-aggregates-in-docs` hit is the *third* consecutive
run to take it (Cantina, Store, now this one), for the same reason each time: a run file is prose
*about* an enumerated list, so every summary sentence wants to count something. Store's run already
proposed a grep gate before the run-file commit; this run is more evidence for it.

The badge finding is the more interesting one, because the dedup **caused** it. Collapsing two
copies of the colour map into `Enum.GetValues(...).ToDictionary(s => s.GetBadgeClass())` registered
every future status with `GetBadgeClass`'s fallback arm, which meant `EnumBadgeMap.For`'s
unhandled-value warning could never fire again — the dedup traded a detection mechanism for the
duplication it removed, exactly the shape of Onboarding's "a dedup that costs a documented rule is
not a win". The fix keeps the dedup and pays the signal back with interest: the fallback arm now
throws, and because the projection runs inside `Section.Register`, a status added without a colour
fails `AddSections()` at startup rather than logging a warning nobody reads. **A dedup that folds a
fallback into a registry deletes that registry's ability to detect a gap — check what the collapsed
copy was doing that the survivor is not.**

**The retracted finding.** A transient local build failure was reproduced on the anchor commit in a
cold worktree and written up as a repo-level defect — that a fresh clone cannot build. CI's own
clean-checkout build refuted it within minutes. The reproduction was sound; the inference from one
cold environment to "the repository" was not, and it went out in a notification before any
independent signal had been sought. **A finding about the build system needs a second, independent
builder before it is a finding — CI is sitting right there, and on this run it was already running.**

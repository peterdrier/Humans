## Assessment summary

Gdpr is at its target structurally and nowhere near it in prose. The section is a
contracts leaf plus one internal orchestrator, one internal controller and a `Section.cs`,
which is exactly what its shapes imply — nothing to move, nothing to split, nothing to
delete. Every conformance detector came back clean, `reforge` reports no dead public
surface, and the fan-out seam that dominates its surface score is the architecture working
as designed rather than debt.

What is off-target is what the section says about itself. Its stated reason for its own
shape was false in three files: they claimed the contracts leaf is a separate project
because `Humans.Base` *implements* `IUserDataContributor`, so a folder would cycle. Base
implements nothing of the sort, does not reference the leaf, and the folder arrangement
would compile. The true reason is better and simpler — the contract is implemented from
*outside*, by every section owning user-scoped tables, so a folder would drag all of them
into referencing `Humans.Gdpr` itself. Alongside that sat a crop of ordinary rot: a
renamed interface, a renamed extension class, two "and nothing else" claims that were not
true, and a target shape whose §1, §2 and §5 still described an export-only section
months after the erasure loop moved in.

The one judgement call the run could not make itself is the merge-chain asymmetry:
`EraseForUserAsync` documents that its caller walks the chain and Users does, while
`ExportForUserAsync` has no such clause and neither caller walks it. Article 15 is
therefore narrower than Article 17 for a merged account. That is a compliance question,
not a tidiness one, and it is in Needs Peter.

Independence check: pass. Findings 1, 6, 8, 16 and 22 came from the target, not from a
tool: 1 and 6 are spec-against-reality deltas, 16 is a partial abstraction (one half of one
interface centralises merge-chain handling and the other distributes it), 8 is a shape
mismatch between the fan-out's roster doc and the roster, and 22 is a lane mismatch. No
tool, score or grep reports any of them — `reforge` reports only the fan-out seam, which
the target had already ruled blessed, and every conformance detector came back clean.

## Retro

**What the selector got wrong: nothing, but it under-sold the section.** Gdpr came up on
age-plus-churn with seventeen lines changed since its last run merged, which reads like a
quiet section due for a routine pass. The seventeen lines were not the story — the story
was a rationale that had been false since a project tier was deleted, which no churn metric
can see because the code it described stopped existing somewhere else. The selector cannot
be blamed for that, but it is worth recording that a low-churn re-doctor tier found the
highest-value finding of the run.

**Wasted motion: waiting, and the order of Phase 3.** Two things. First, the run dispatched
the Phase 3d threads before writing the Phase 3c target, reversing the skill's order. The
damage was contained — the tool-free 3b reading had already found the §5, §2 and §1
staleness before any thread returned, so the target was not contaminated by thread output
— but the ordering exists so that the target is written blind, and this run did not honour
it. Second, waiting on the reviewer burned real time on background sleeps that did not
advance the clock, because each was launched detached and polled immediately; a foreground
blocking loop fixed it. Neither is a project rule, so neither becomes an atom.

**What striking revealed that the assessment missed: finding 12 was wrong.** The Tests
thread called two export tests overlapping, the ranked list carried it as a dedup, and it
survived to the strike. Reading the orchestrator alongside them to make the cut showed they
pin the two nested loops — the assessment had compared their assertions and not their
inputs. Having a finding die on the table is the system working, but it is a reminder that
"these two tests look alike" is a hypothesis about the code under test, not about the tests.

**What the target diff says: the shape was right and the story was wrong.** Section 3 of
the regenerated target says the same thing the old one did — a contracts leaf, one
orchestrator, one controller, one `Section.cs` — and the run changed no structure at all.
Everything that moved was an explanation. That is the signature of a section that is
finished and a doc set that is not, and it argues for re-doctoring on prose-age rather than
code-churn: the code stopped changing, which is exactly why nobody reread what it says
about itself.

**Deviations recorded.** The branch is `section-doctor/2026-09-17T011559Z` rather than the
`claude/…` name the harness boilerplate supplied, because every `doctor.py` subcommand
derives run identity from the branch name. `docs/features/global/gdpr-export.md` sits
outside `src/Sections/Humans.Gdpr/` and was judged in scope: it is the fan-out's roster
doc, it documents no section but this one's contract, and its drift is Gdpr's drift.

**Trace misses, checked by hand.** `doctor.py trace` reports `IGdprExportService`,
`NodaTimeFormattingExtensions` and `ErasedUserId` as unresolvable. That is the point: each
is a name this run deleted, quoted in `## Findings` to say what the prose used to claim.
`GdprResource` misses because `Docs/health.md` lists it under deliberately-not-done.
`/Profile/Me/DownloadData` reads as `CHECK` because the literal is split across attributes;
`ProfileController` carries `[Route("Profile")]` with `[HttpGet("Me/DownloadData")]` on the
action, and the action takes a cancellation token and no id.

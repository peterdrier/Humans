## G1 gap list

1. **`docs/sections/Search.md` doesn't exist** (predicate 7). Fix: write it, distinguishing the global `/Search` page (this section) from the `HumanSearchViewComponent` picker widget (Users-owned) per the scope note above — that distinction isn't written down anywhere today and is exactly the kind of thing a future contributor would get wrong. No-migration-needed: **y**.
2. **`SearchService` implements `IApplicationService`, not `IOrchestrator`, despite matching the orchestrator definition exactly and being classified as one in the frozen inventory** (see Observation above). Fix (follow-up, not required by any failing predicate): either reclassify `SearchService`/`ISearchService` to `IOrchestrator`, or correct the frozen-inventory doc's classification — flag for Peter, low urgency since no analyzer currently depends on the answer. No-migration-needed: **y**.
3. **The public-surface privacy guarantee is already violated on the GUID path — a code gap, not just a coverage gap** (see G3 gap #1 for the test side). `ISearchService.cs:22-26` promises "hidden teams, non-public camp seasons, admin-only rotas … are excluded for everyone, regardless of role", but `SearchService.SearchAsync` gates only on `trimmed.Length < 2` (`SearchService.cs:43`) — a pasted 36-char GUID sails through to every bucket, and three of the four resolve it by id *around* their own visibility filter:
   - `CachingTeamService.SearchAsync` (`CachingTeamService.cs:154-160`) — returns the team by id "**any visibility**", bypassing the `IsActive && !IsHidden` filter applied to name matches.
   - `CachingCampService.SearchAsync` (`CachingCampService.cs:134-143`) — returns the camp by id "**any status**", bypassing `PublicCampSeasonStatuses`.
   - `ShiftManagementService.SearchAsync` (`ShiftManagementService.cs:465-472`) — calls `repo.GetRotaAsync(id, …)` directly instead of `SearchVolunteerVisibleRotasAsync`, so an admin-only rota resolves by id.

   So any authenticated user holding a hidden team's / non-public camp's / admin-only rota's GUID gets its name back from `/Search`. Each bypass is deliberate parity with a pre-existing by-id path (the code comments say "mirroring the old by-id path"), so this is inherited behaviour rather than a regression introduced by the caching rewrite — but it contradicts the guarantee as written, and no predicate catches it because Search owns no tables and leaks no entities. Users is the one bucket that gets this right: `CachingUserService.SearchUsersAsync` (`CachingUserService.cs:127-135`) has the same paste-a-GUID affordance but still filters (`Profile is not null && RejectedAt is null`) and documents the intent. Fix — Peter's ruling needed on which way to close the gap: either narrow the three by-id paths to respect their visibility filters, or amend the `ISearchService` doc comment to carve out GUID lookups as a sanctioned "you already had the id" affordance the way Users does. No-migration-needed: **y**.
4. **The Shifts bucket depends on the full write-capable service, not a read contract** (predicate 1). `SearchService` reaches Shifts through `IShiftManagementService` — 46 async methods, write methods included (`CreateShiftAsync`, `UpdateShiftAsync`, `DeleteEventAsync`, `DeleteShiftProfilesForUserAsync`, `CreateBuildStrikeShiftsAsync`) and 9 EF-entity-returning reads in `ApplicationServiceEntityReadReturns.baseline.txt:13-21` — while every other bucket uses a `*ServiceRead`. It calls exactly one method, `SearchAsync`.

   Not a hard-rule violation as written: the rule is "must be via the `I<section>ServiceRead` **when available**", and no `IShiftManagementServiceRead` exists. But the pattern is established *inside Shifts itself* — `IVolunteerTrackingServiceRead` sits in the same folder — so this is the read-split simply not having reached the section's largest interface, not an architecture that lacks the concept. The practical cost is that Search, an orchestrator that only ever reads, holds a handle capable of deleting an event, and inherits a slice of the entity-leak baseline it has no use for.

   Fix: carve `IShiftManagementServiceRead` out per [`memory/architecture/section-read-write-split.md`](../../../memory/architecture/section-read-write-split.md) (the `section-read-split` skill automates this; Teams/PR 678 is the reference) and migrate Search's one call to it. Scope note for whoever picks it up: this is a **Shifts** work item that Search benefits from, not a Search-local fix — the interface belongs to Shifts, and Search is one of presumably several cross-section callers, so it should be sized against Shifts' full caller list rather than this scorecard alone. No-migration-needed: **y**.
5. **`ISearchService`'s own doc comment is stale in two ways, and it is the contract every other Search doc defers to** (predicates 3, 7). It says the service "returns four independently-ranked buckets" and lists the fan-out as `IProfileService`, `ITeamService`, `ICampService`, `IShiftManagementService` (`ISearchService.cs:5-14`). Both parts are wrong against `SearchService.cs:54-66`: there are **five** buckets — Humans, Teams, Camps, Shifts, Events, the last gated on `Features:Events` — and three of the four named interfaces aren't what's injected (`IUserServiceRead`, `ITeamServiceRead`, `ICampServiceRead` are, alongside `IEventServiceRead`, which the comment omits entirely). This matters more than a normal stale comment: no `docs/sections/Search.md` exists (G1 gap #1), so this comment *is* the section's contract of record, and both the missing tests (G3 gap #1) and the privacy guarantee (G1 gap #3) are written against it. Fix: correct the comment alongside whichever of those lands first, and fold the Events bucket into the section doc when gap #1 is written. No-migration-needed: **y**.

## G3 gap list

1. **`SearchService`/`SearchController` have zero test coverage of any kind** (predicates 2, 3, 5) — the min-length query gate, the five-bucket fan-out (Humans, Teams, Camps, Shifts, and Events when `Features:Events` is on — see G1 gap #5), the `onlyType` filter, the exact/prefix/contains scoring tiers, the `Features:Events` gate, and the public-surface-only privacy guarantee ("hidden teams, non-public camp seasons, admin-only rotas, and admin-only profile fields are excluded for everyone, regardless of role" per `ISearchService.cs`'s own doc comment) are all unverified by any automated test. This is the single largest gap found across all five sections in this audit — a privacy-relevant guarantee with no regression protection. **And the absence of tests is how the guarantee came to be broken unnoticed:** on GUID queries three of the four buckets resolve by id around their own visibility filters (G1 gap #3), so the regression test to write here is not merely a guard against future drift — it fails today. Fix: add `SearchServiceTests.cs` mocking the five injected `*ServiceRead`/service interfaces, covering at minimum the query-length gate, `onlyType` short-circuit, and score-tier boundaries; add `SearchControllerTests.cs` for the sort/view-model assembly. Write the hidden-team / non-public-camp / admin-rota GUID cases to whichever contract Peter settles in G1 gap #3, so the tests and the doc comment land in agreement. No-migration-needed: **y** (test-only change, no schema involved).

**Scope note:** Search's `reforge.surface-score.json` entry (`paths`/`symbols`/`serviceInterfaces: [ISearchService]`) covers the global `/Search` page only. `src/Humans.Web/ViewComponents/HumanSearchViewComponent.cs` — a reusable inline person-picker widget backed directly by `IUserServiceRead` — is a distinct, Users-owned UI component that happens to share the word "search"; it is correctly excluded from the reforge Search paths and is out of scope here.

3. ~~**The public-surface privacy guarantee is already violated on the GUID path — a code gap, not just a coverage gap**~~ **→ RULED not a gap, 2026-08-07 (nobodies-collective/Humans#985); see the ruling at the end of this entry. The original finding is kept below for the record.** As audited: `ISearchService.cs:22-26` promises "hidden teams, non-public camp seasons, admin-only rotas … are excluded for everyone, regardless of role", but `SearchService.SearchAsync` gates only on `trimmed.Length < 2` (`SearchService.cs:43`) — a pasted 36-char GUID sails through to every bucket, and three of the four resolve it by id *around* their own visibility filter:
   - `CachingTeamService.SearchAsync` (`CachingTeamService.cs:154-160`) — returns the team by id "**any visibility**", bypassing the `IsActive && !IsHidden` filter applied to name matches.
   - `CachingCampService.SearchAsync` (`CachingCampService.cs:134-143`) — returns the camp by id "**any status**", bypassing `PublicCampSeasonStatuses`.
   - `ShiftManagementService.SearchAsync` (`ShiftManagementService.cs:465-472`) — calls `repo.GetRotaAsync(id, …)` directly instead of `SearchVolunteerVisibleRotasAsync`, so an admin-only rota resolves by id.

   So any authenticated user holding a hidden team's / non-public camp's / admin-only rota's GUID gets its name back from `/Search`. Each bypass is deliberate parity with a pre-existing by-id path (the code comments say "mirroring the old by-id path"), so this is inherited behaviour rather than a regression introduced by the caching rewrite — but it contradicts the guarantee as written, and no predicate catches it because Search owns no tables and leaks no entities. Users is the one bucket that gets this right: `CachingUserService.SearchUsersAsync` (`CachingUserService.cs:127-135`) has the same paste-a-GUID affordance but still filters (`Profile is not null && RejectedAt is null`) and documents the intent.

   **RULED, 2026-08-07 (nobodies-collective/Humans#985) — not a code gap. The doc comment was wrong, not the code.** Peter's ruling: by-GUID lookups get no visibility filter — you must already hold the id, and the destination page is the enforcement point ("if the user isn't entitled to see it, they'll get an error when they click on the search result"). **Text queries are unchanged and still filtered** — the ruling does not open hidden teams / non-public camp seasons / admin-only rotas to name search. So the fix is the second option, not the first: **do not narrow the three by-id paths.** What remains open is (a) rewriting the stale `ISearchService` doc comment (see gap #5) and (b) the ruling's one new, load-bearing item — tests that the *destination* pages actually reject, since the guarantee now lives entirely there. That check has already found one hole: `/Camps/{slug}` and `/Camps/{slug}/Season/{year}` have no season-status gate, filed as nobodies-collective/Humans#993. Recorded in [`src/Sections/Humans.Search/Docs/Search.md`](../../../src/Sections/Humans.Search/Docs/Search.md). No-migration-needed: **y**.
4. **The Shifts bucket depends on the full write-capable service, not a read contract** (predicate 1). `SearchService` reaches Shifts through `IShiftManagementService` — 46 async methods, write methods included (`CreateShiftAsync`, `UpdateShiftAsync`, `DeleteEventAsync`, `DeleteShiftProfilesForUserAsync`, `CreateBuildStrikeShiftsAsync`) and 9 EF-entity-returning reads in `ApplicationServiceEntityReadReturns.baseline.txt:13-21` — while every other bucket uses a `*ServiceRead`. It calls exactly one method, `SearchAsync`.

   Not a hard-rule violation as written: the rule is "must be via the `I<section>ServiceRead` **when available**", and no `IShiftManagementServiceRead` exists. But the pattern is established *inside Shifts itself* — `IVolunteerTrackingServiceRead` sits in the same folder — so this is the read-split simply not having reached the section's largest interface, not an architecture that lacks the concept. The practical cost is that Search, an orchestrator that only ever reads, holds a handle capable of deleting an event, and inherits a slice of the entity-leak baseline it has no use for.

   Fix: carve `IShiftManagementServiceRead` out per [`memory/architecture/section-read-write-split.md`](../../../memory/architecture/section-read-write-split.md) (the `section-read-split` skill automates this; Teams/PR 678 is the reference) and migrate Search's one call to it. Scope note for whoever picks it up: this is a **Shifts** work item that Search benefits from, not a Search-local fix — the interface belongs to Shifts, and Search is one of presumably several cross-section callers, so it should be sized against Shifts' full caller list rather than this scorecard alone. No-migration-needed: **y**.
5. **`ISearchService`'s own doc comment is stale — in four ways** (predicates 3, 7). Audited as two; the 2026-08-07 update inline below adds two more and demotes it from contract-of-record. It says the service "returns four independently-ranked buckets" and lists the fan-out as `IProfileService`, `ITeamService`, `ICampService`, `IShiftManagementService` (`ISearchService.cs:5-14`). Both parts are wrong against `SearchService.cs:54-66`: there are **five** buckets — Humans, Teams, Camps, Shifts, Events, the last gated on `Features:Events` — and three of the four named interfaces aren't what's injected (`IUserServiceRead`, `ITeamServiceRead`, `ICampServiceRead` are, alongside `IEventServiceRead`, which the comment omits entirely). ~~This matters more than a normal stale comment: no `src/Sections/Humans.Search/Docs/Search.md` exists (G1 gap #1), so this comment *is* the section's contract of record~~ — **no longer true as of 2026-08-07:** [`src/Sections/Humans.Search/Docs/Search.md`](../../../src/Sections/Humans.Search/Docs/Search.md) now exists (gap #1 resolved, nobodies-collective/Humans#986) and is the section's contract of record; the Events bucket is folded into it. The comment is demoted from contract to stale duplicate — but it is still stale, and now in a **third** way the audit missed: it says each section "runs its own case-insensitive Postgres ILike query at the DB layer", which is wrong for four of the five buckets — Humans, Teams, Camps and Events are all served from their section's in-memory cache (`CachingUserService`/`CachingTeamService`/`CachingCampService`/`CachingEventService`), and Shifts is the only one that reaches Postgres. It is also stale on the privacy guarantee, which #985's ruling superseded (gap #3).

   **Update 2026-08-07 — three of the four fixed by #1198, one not.** The merged comment now says "five independently-ranked buckets", names the five interfaces actually injected, and replaces the old guarantee with "**Search is not an authorization boundary**" (citing both #993 and #998). **The cache-vs-DB point is only half fixed:** it reads "from a cached snapshot for teams/camps/humans, via Postgres ILike at the DB layer for rotas *and events*" (`ISearchService.cs:10-12`). Events is still wrong — `EventsSectionExtensions.cs:48` registers `IEventServiceRead` as the `CachingEventService` singleton, whose `GetApprovedEventsAsync` filters `_eventCache.Values` through `MatchesQuery` (`:327-329`) with no DB round trip. Shifts is the only DB-backed bucket. Remaining fix is one clause in that comment. No-migration-needed: **y**.

# Pleo connector — design

**Status:** Draft — awaiting Peter's sign-off
**Date:** 2026-08-10
**Context:** ~5 members hold Pleo cards funded by a 30k transfer from Sabadell. Holded ledger `57200003` shows D 30,000.00 / C 71.97 — ~29,928 of card spend is booked nowhere in Holded and invisible to the 629 actuals. Goal: mirror Pleo's transactions into Humans, map them to the 629 departments, and (phase 2, needs a Holded write key) book them into Holded for one consolidated spend view.

## Pleo API facts (from developers.pleo.io, 2026-08-10)

- Base `https://external.pleo.io` (staging: `external.staging.pleo.io`). **Standalone API key** auth = HTTP Basic, key as username, empty password. Keys are generated by an org admin in the Pleo web app **but are not self-service — Pleo must enable them for the org during onboarding**; that request is step 0. Requests carry a `company_id` query param.
- **Accounting Entries API** is the read source (the old Expenses API is deprecated): `POST /v1/accounting-entries:search` — cursor pagination (max 100/page, `total` included), filters on bookkeeping/performed/settled date ranges, status (`DRAFT…COMPLETED…`), export status, families (`CARD_PURCHASE`, `OUT_OF_POCKET`, …), employees, categories. Entry fields: `id`, `family`/`subFamily`, `status`, `exportStatus`, `reviewStatus`, `transactionValue {currency, minors}`, `totalBillValue` (company currency), `performedAt`/`settledAt`/`bookkeepingDate`/`updatedAt`/`deletedAt`, `employeeId`, **`accountId` + `accountCode`** (the Pleo spending category), `taxCodeId`, `merchant {name, mcc,…}`, `supplier`, `note`, `receiptIds[]`, `tags[]`, `splitItems[]` (per-split account/tax/amount).
- Receipts: `GET .../receipts` + receipt file download endpoints — receipt binaries are fetchable for phase-2 attachment to Holded docs.
- **Chart of Accounts API**: full CRUD + batch create on Pleo's category chart — Pleo's categories can be made to carry our Holded 629 codes.
- Webhooks exist but document only `v1.export.job-created` and `v1.vendor.created` — nothing entry-level, so the mirror polls. Volume is tiny (~5 cards), so that costs ~2–3 calls/night.
- Rate limits: not documented; nothing in this design exceeds a handful of calls per day.
- Master OpenAPI: `https://developers.pleo.io/openapi.json` — pin DTOs against it at implementation time.

## Design

Mirrors the Holded-section pattern exactly (see `2026-08-10-holded-v2-migration-design.md`):

**Connector (Base):** `IPleoClient` (Humans.Application/Interfaces/Pleo) + `PleoClient` (Humans.Infrastructure): `SearchAccountingEntriesAsync` (cursor-paged, date-range + status filters), `ListAccountsAsync` (chart of accounts), `GetReceiptFileAsync`. Config: `PLEO_API_KEY` env var (skip-when-unset like Holded), `Pleo:CompanyId`. Same typed transient/permanent exception split; per-call metering can reuse the pattern but its own `IPleoCallLog` only if a quota ever materializes — omit for now (YAGNI at 3 calls/night).

**Section `Humans.Pleo` (G5):** own `PleoDbContext`:
| Table | Content |
|---|---|
| `pleo_entries` | mirror of accounting entries: PleoId (key), family, status, export/review status, amount (from `totalBillValue`, EUR), original currency+minors, performed/settled/bookkeeping dates, employee id + resolved name, merchant name, `accountCode` (→ 629 mapping), note, receipt count, deleted flag, synced-at |
| `pleo_accounts` | Pleo category chart cache (id, name, code) |
| `pleo_sync_states` | kind-keyed, same shape as Holded's |

Sync: **nightly full sweep with replace semantics** — the whole entry history is ≤ a few hundred rows = 1–3 calls, so no window logic at all; deleted/edited entries can never linger (the lesson of the Holded stale-line bug, applied from birth). Same non-blocking sweep gate. `Contracts` leaf only if/when another section consumes Pleo data — start with **no** Contracts project (nothing consumes it yet; the admin screen is section-internal).

**Screen `/Pleo`:** sync state + sync-now; entries table (date, employee, merchant, amount, status, 629 code, booked-in-Holded later); per-employee and per-629 totals; a **reconciliation card**: Pleo spend total (COMPLETED entries) vs Holded `57200003` movement (currently 30,000 in / 71.97 booked) — the visible "unbooked spend" gap.

**Categorization — per-cardholder mapping (primary; Peter, 2026-08-10):** each Pleo card is held by one department's lead, so an entry's department = its cardholder's department. New table `pleo_employee_map` (PleoEmployeeId → Holded 629 account number), seeded by hand on the `/Pleo` screen; every entry inherits its cardholder's account, with per-entry override possible later. Live-verified 2026-08-10 (all four cardholders resolved via `GET /v2/employees?companyId=…`; card spend joins exactly, −40,600.94 total): Zak Bulpitt −23,989.44 → La Cantina `62900114`; Daniela Marquez −9,300.82; Toby Walpert −5,556.78; Deepak Voigt −1,753.90 (last three mappings TBC by Peter at implementation). Zero of 223 entries carry an `accountCode`, so Pleo-side chart alignment is NOT the mechanism — it stays a possible later refinement only if per-entry categorization inside Pleo ever starts happening.

**Live-probed facts (2026-08-10, read-only key):** company id via `GET /v1/introspect` → `subjectURN` (`urn:pleo:company:{id}`); key + company id stored beside the Holded dev token (`~/.holded/pleo-dev-token`, `pleo-company-id`). Scopes: accounting-entries/accounts/users/vendors/tax-codes/export-items/tag-groups/companies, all read. 223 entries 2026-06-08→08-01, all `COMPLETED`; sign convention: wallet loads positive, card spend negative. Wallet loads total **60,000** (10,000 + 19,980 + 30,000 + 20 test). Holded's `57200003` correctly books the three June loads (entries #1955/#1954/#2058 = 30,000 D) but the 30 June 30,000 load has no journal entry yet — its Sabadell movement sits unreconciled (Peter fixes in the GUI). Card spend booked in Holded: one 71.97 line (Deepak) out of ~40,600 — that spend gap is the connector's reason to exist. 205/223 entries have receipts. Employee list endpoint is `GET /v2/employees` (the `/v1/employees|users` paths RBAC-deny this key).

**Phase 2 — booking into Holded (needs the write key; separate design):** two candidate shapes, decision deferred to Peter + accountant:
(a) one Holded purchase doc per Pleo entry, receipt attached, `items[].account` = 629 code, paid from the Pleo treasury account — full document trail;
(b) periodic aggregate journal entry (`POST /api/v2/ledger-entries`) debiting the 629 accounts, crediting `57200003` — lighter, no per-transaction docs.

## Out of scope

- Any Holded write (phase 2).
- Webhooks (nothing entry-level exists to subscribe to).
- OAuth (single-company standalone key is the fit).

## Notable surprises

- **Two sections still import the dying hub directly for live functionality**, not just legacy scaffolding: `Humans.GoogleIntegration`'s own `DbContext` does `using Humans.Domain.Entities` for 3 of its `DbSet<>`s, and `Humans.Auth`'s own docs/tests explicitly pin `MagicLinkService` as staying in "Base" rather than moving into Auth — i.e., the target isn't "empty Application into sections," some of this is destined to *stay* in the hub's replacement (Base), by already-recorded architectural decision, not oversight.
- **`AuditViewerService` and `MagicLinkService` are not undecided** — I initially expected these (per the task's "known undecided candidates" framing implied by their names) to need a placement call, but both have written, reasoned decisions already on record in their respective section docs/tests. Worth flagging so the 4a session doesn't re-litigate them.
- **`ITicketVendorService` is a real inter-section abstraction**, not hub debt: `Humans.Tickets` defines the need, `Humans.TicketTailor` implements it. This is exactly the "another section's impl project directly, no cycle" case the design doc calls out — no `.Contracts` leaf needed if Tickets owns it and TicketTailor references Tickets directly.
- **No dead code found** in this scope. Everything still has at least one real caller — this hub is thin now (866 has been chewing through it steadily) but not yet rotting.

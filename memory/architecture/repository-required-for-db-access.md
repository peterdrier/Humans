---
name: repository required for every DB-accessing service
description: HARD RULE. Every service that reads or writes a DB table goes through a repository class; no service injects a DbContext directly, even for singleton-row tables. The repository is required; a repository *interface* is not, unless something needs the seam.
---

If a service stores or reads anything in the database, it goes through a repository class. No exceptions — not for singleton-row settings tables, not for "trivial" lookups, not for "this is a tiny convenience" cases.

**The repository is mandatory; its interface is not.** The rule is about which type may hold the DbContext, not about indirection. Pre-split (a service in `Humans.Application`, a repository in `Humans.Infrastructure`) the interface is what lets the service name the repository across the assembly boundary, so it stays. Inside a G5 section assembly (nobodies-collective/Humans#866) there is no boundary to cross: `internal sealed class Repository` is the whole thing, and an interface is only added when something actually needs the seam — a caching decorator ([`decorators-talk-only-to-inner`](decorators-talk-only-to-inner.md) requires one to wrap) or a cross-section entry in the section's `Contracts/`.

**Why:** The Application layer cannot reference EF types (`HumansDbContext`, `DbSet<T>`, `IQueryable`). The repository boundary is what keeps that rule enforceable: every DB call has a thick, materialized-list repository method behind it. The moment one service smuggles in `HumansDbContext` directly, the layer rule has a hole, and reviewers stop noticing the next one. Past instance: `AgentSettingsService` was originally written to inject `HumansDbContext` (singleton-row table, "why bother with a repo"). Refactored in `1f113b60` to use `IAgentRepository` and the rule snapped back into place.

**How to apply:** New service touches the DB → in a pre-split section, define the repository interface in `Humans.Application/Interfaces/Repositories/I<Section>Repository.cs`, implement in `Humans.Infrastructure/Repositories/<Section>/<Section>Repository.cs`, then build the service on top; in a G5 section project, write `Data/Repository.cs` and build the service on it, no interface. Either way the repository is the only type that may hold the DbContext. If the section has one settings row, the repository still exists — it has `GetSettingsAsync`/`SaveSettingsAsync` methods. If you find yourself writing `_db.Set<T>()` inside an Application service, stop and add a repository method instead. See also [`no-linq-at-db-layer`](no-linq-at-db-layer.md).

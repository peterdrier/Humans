name: health-data-audited-reveal
description: Health data (medical conditions, allergy/intolerance free text) never renders on a page; it opens behind an audited reveal POST; a single-person reveal is listed to the member, a roster reveal writes one scope row.
type: code
---

Medical conditions and allergy / intolerance details (GDPR Art. 9) are never in page HTML, search JSON or a DTO a view serializes. The page shows a reveal control to holders of the narrow policy; the click is a POST that writes an `IAuditLogService` entry (actor, subject or scope) and only then returns or renders the text. The subject sees every reveal of their own data.

**Why:** Peter, 2026-10-22: "Health data opens behind an audited reveal, audit visible to subject, Board, admins." Board can see everything but change nothing, and sensitive personal data has to leave a trace each time somebody looks. The IBAN reveal (`PaymentDetailsAdminController.RevealIban`) set the pattern.

**How to apply:** Live examples: Users' `POST /Profile/{id}/Medical/Reveal` (`MedicalConditionsRevealed`, entity `User`, JSON back to the Shifts roster badge; listed on `/Profile/Me/Medical`) and Cantina's `POST /Cantina/Roster/RevealHealth` (`CantinaHealthDetailsRevealed`, one-render TempData token scoped to the week or day). A new health field gets the same shape: the owning section is its only reader (never on a cached read model other sections see), a POST that audits before disclosing, and a `<vc:audit-log>` on the member's own page. A reveal on a role's working list (a roster assembling many people's answers) writes **one** row for the scope, never one per member shown: Peter, 2026-10-30, "this is the kitchen manager assembling allergies across 200 people", not someone poking at one person's health data. The member-page list belongs to single-person lookups. Never add the text to a `*ViewModel` or search projection "because the role is already checked"; the check decides who may reveal, the audit records that they did. Another section that shows the button (Shifts' roster) knows only that the viewer passes the policy, never whether text exists: Peter, 2026-11-07, "shifts shouldn't know about a user's medical history".

`BackdoorApiKeyHandler` (`Authentication/BackdoorApiKeyHandler.cs`) is the `BackdoorApiKey` authentication scheme: it resolves the `X-Api-Key` header to the human who owns the key and returns a principal carrying their id (`ClaimTypes.NameIdentifier`). A missing, unknown, revoked or expired key fails alike. It is never a default scheme. `BackdoorApiKeyAuthFilter` (`Filters/BackdoorApiKeyAuthFilter.cs`) runs it for the REST controllers, answers 401 on failure and installs the principal. `[AllowAnonymous]` on each API controller only opts out of the authenticated-by-default fallback policy so the filter can run; there is no cookie path and no unauthenticated endpoint under `/api/backdoor/*`.

The Shell's claims transformation runs on the key principal as on any sign-in, adding the owner's active roles and account state, so `User.IsInRole` behaves as for a cookie-authed session and everything served scopes to the key's owner. `MembershipRequiredFilter` and `NameRequiredFilter` (`src/Humans.Web/Authorization/`) pass REST key requests through because every key-authed controller is `[AllowAnonymous]`, rather than redirecting them to an onboarding page — see `docs/authorization-inventory.md` §4.

Every key-authed controller also declares `[BackdoorScope(...)]`; the filter answers 403 when the scope does not admit the key's owner, or when a controller declares none. All declare `AdminAndBoard` (Admin or Board) except `BackdoorTasksController`, which declares `Tasks` (holds `Tasks.Manage` on some team).

Key eligibility (who may hold a key, and who continues to authenticate on each request) is anyone some scope admits, narrowed to accounts in `UserState.Active`; below Admin and Board, keys expire after 30 days — see `Docs/Backdoor.md` for the full invariant.
